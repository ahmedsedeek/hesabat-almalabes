# البنية والقرارات التقنية

## لماذا هذه التقنيات

| القرار | السبب |
|---|---|
| **Electron** | نفس الشيفرة تعمل على Windows و macOS، ومحرّك Chromium يتكفّل بتشكيل الحروف العربية والاتجاه من اليمين لليسار في الشاشة وفي ملفات PDF معًا — وهي أصعب نقطة في التطبيقات العربية. |
| **SQLite (better-sqlite3)** | قاعدة علائقية حقيقية بملف واحد: لا خادم، لا إعداد، نسخ احتياطي بنسخ ملف، معاملات ACID كاملة، وأداء ممتاز حتى مئات الآلاف من السجلات. الواجهة متزامنة فتُبسّط كتابة المعاملات المالية. |
| **React + TypeScript** | أنواع صارمة على الحدود المالية، وواجهة قابلة للصيانة والتوسّع. |
| **القيد المزدوج** | يجعل كل رقم في النظام قابلًا للتتبّع والتدقيق، ويكشف أي خلل تلقائيًا عبر ميزان المراجعة. |

## الطبقات

```
┌────────────────────────────────────────────────┐
│  الواجهة (renderer) — React RTL                │
│  لا تعرف شيئًا عن SQL أو نظام الملفات          │
└───────────────────┬────────────────────────────┘
                    │ window.api.invoke(channel, payload)
┌───────────────────▼────────────────────────────┐
│  الجسر (preload) — contextBridge، قناة واحدة   │
└───────────────────┬────────────────────────────┘
                    │ ipcMain.handle('api:invoke')
┌───────────────────▼────────────────────────────┐
│  طبقة المسارات (ipc) — جلسة + صلاحية + أخطاء  │
└───────────────────┬────────────────────────────┘
┌───────────────────▼────────────────────────────┐
│  خدمات المجال (services)                        │
│  مبيعات · مشتريات · إنتاج · مدفوعات · مصروفات   │
└──────┬──────────────────────┬───────────────────┘
       │                      │
┌──────▼────────┐   ┌─────────▼─────────┐
│ دفتر الأستاذ  │   │ المخزون الدائم    │
│ (القيد المزدوج)│   │ (المتوسط المرجَّح) │
└──────┬────────┘   └─────────┬─────────┘
       └──────────┬───────────┘
            ┌─────▼──────┐
            │  SQLite    │
            └────────────┘
```

**قاعدة ثابتة:** الواجهة لا تحتوي على أي منطق مالي. كل حساب يظهر على الشاشة
له مصدر واحد في النواة، والواجهة تعيد حسابه فقط لمعاينة الإجماليات قبل الحفظ
باستخدام **نفس** الدوال المشتركة في `src/shared/money.ts` حتى لا يختلف المعروض عن المحفوظ.

## تمثيل المبالغ

لا تُستخدم الأعداد العشرية (float) لأي قيمة مالية.

| النوع | المقياس | المثال |
|---|---|---|
| مبلغ (إجمالي، قيد، رصيد) | `×100` | `12.34` تُخزَّن `1234` |
| سعر أو تكلفة وحدة | `×10000` | `12.3456` تُخزَّن `123456` |
| كمية | عدد عشري بدقة ٣ خانات | `800.5` متر |

سبب المقياسين: الإجماليات يجب أن تطابق العملة تمامًا، بينما تكلفة الوحدة
تحتاج دقة أعلى حتى لا يتراكم خطأ التقريب عبر آلاف الحركات.

توزيع الخصومات وتكاليف الشحن يستخدم `allocate()` التي تضمن أن **مجموع الأنصبة
يساوي المبلغ الأصلي تمامًا** (الوحدات المتبقية تُوزَّع على الأسطر ذات أكبر كسر).

## التواريخ

كل التواريخ تُخزَّن كنص `YYYY-MM-DD` **بالتوقيت المحلي**.
`toISOString()` محظورة في منطق التواريخ لأنها تحوّل إلى UTC فتُرجِع اليوم السابق
في البلدان التي تسبق التوقيت العالمي — وهو خطأ خطير في تأريخ الفواتير.
البديل في `src/shared/date.ts`.

## المعاملات وسلامة البيانات

كل عملية مالية تُنفَّذ داخل معاملة SQLite واحدة (`IMMEDIATE`):

```
فاتورة بيع = سجل الفاتورة
           + أسطرها
           + حركات إخراج مخزني (تحديث الرصيد والمتوسط)
           + قيد محاسبي متوازن (إيراد + ضريبة + خصم + تكلفة البضاعة المباعة)
           + سند قبض إن وُجدت دفعة
```

إن فشلت أي خطوة — ولو كانت «الكمية غير كافية» — لا يُحفظ شيء إطلاقًا.
هذا مُغطّى باختبار صريح يتأكد أن عدد القيود لم يتغيّر بعد محاولة فاشلة.

إعدادات قاعدة البيانات المختارة لحماية البيانات:

| الإعداد | القيمة | السبب |
|---|---|---|
| `foreign_keys` | ON | منع السجلات اليتيمة |
| `journal_mode` | WAL | أمان أعلى عند الانهيار وأداء أفضل |
| `synchronous` | FULL | عدم فقدان أي معاملة مُثبَّتة عند انقطاع الكهرباء |
| `busy_timeout` | 8000 | تفادي أخطاء القفل عند الوصول المتزامن |

## الأمان

- كلمات المرور بـ **bcrypt** (11 جولة)، وقفل الحساب ١٥ دقيقة بعد ٥ محاولات خاطئة.
- `contextIsolation: true`، `nodeIntegration: false`، وقناة IPC واحدة فقط.
- سياسة محتوى (CSP) صارمة في الواجهة: لا سكربتات خارجية ولا اتصالات شبكية.
- فحص الصلاحية يحدث **في النواة** لكل استدعاء، لا في الواجهة فقط.
- الروابط الخارجية تُفتح في المتصفح، ولا يُسمح بفتح نوافذ جديدة داخل التطبيق.
- النسخ الاحتياطية تُشفَّر بـ AES-256-GCM بمفتاح مشتق عبر scrypt.

## الأخطاء

المستخدم لا يرى نصًا تقنيًا أبدًا. كل خطأ متوقَّع يُرمى كـ `AppError`
برسالة عربية جاهزة؛ وأي خطأ غير متوقَّع يتحوّل إلى
«تعذّر حفظ العملية. يرجى التحقق من البيانات والمحاولة مرة أخرى.»
وتُكتب تفاصيله التقنية في `logs/` فقط.

## الطباعة وملفات PDF

تُبنى المستندات كـ HTML عربي RTL مع **خط Cairo مضمَّن كـ base64**، ثم تُحوَّل
عبر `webContents.printToPDF`. بهذه الطريقة يتكفّل Chromium بربط الحروف والتشكيل
والاتجاه، ويظهر المستند بنفس الشكل على ويندوز وماك — على عكس مكتبات PDF
التي تتطلب معالجة يدوية معقّدة للنص العربي.

## التوسّع مستقبلًا

- **لغة إنجليزية:** كل النصوص في الواجهة والقوالب، وحقل `name_en` موجود في شجرة الحسابات،
  و`locale.language` في الإعدادات. الإضافة تتم بطبقة ترجمة فوق النصوص دون تغيير البنية.
- **تعدد العملات:** المبالغ أعداد صحيحة بمقياس معلوم والعملة في الإعدادات؛
  الإضافة تحتاج عمود عملة + سعر صرف على مستوى المستند والقيد.
- **مزوّدات سحابية بـ OAuth:** `BackupService` يعزل وجهة الرفع، والإضافة تتم بتنفيذ
  واجهة رفع جديدة دون المساس بمنطق التشفير والضغط.
